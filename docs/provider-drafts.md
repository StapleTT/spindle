# IMAP Drafts synchronization

Saved local drafts with a selected account synchronize to that account’s designated IMAP **Drafts** folder. Local autosave and browser recovery continue to work while the provider is offline. The composer shows provider status separately from **Saved to Spindle**; that acknowledgement alone does not mean the provider copy is saved.

## Behavior

- A save queues work in the same database transaction. After a three-second debounce, the existing worker mirrors the latest revision, including rich/plain bodies, reply headers, Bcc and ready attachments. No SMTP setup is required for saving drafts. From uses the configured SMTP identity/name when available, otherwise an email-shaped IMAP login; non-email logins do not invent a From address.
- The worker uses only a server-designated `\Drafts` SPECIAL-USE folder. It never guesses a folder name or creates one. Missing folders produce visible failures while preserving local text.
- Native-client drafts are imported from synchronized local metadata, within the account’s selected history coverage. New imports wait for the normal metadata poll and worker dispatch. Known drafts are checked about once a minute. This is polling, not instantaneous push.
- Synchronization pauses while the draft is frozen in Outbox. Native changes are adopted automatically only when the saved local revision still matches the last synchronized revision and the draft is not frozen in Outbox. Open clean editors refresh within five seconds; delayed older poll responses cannot roll back a newer saved revision. Unsaved or unacknowledged browser changes retain their recovery buffer and must pass the existing revision check.
- If both versions changed, neither overwrites the other. **Compare provider version** shows subject, text and attachment count. **Use provider version** explicitly replaces the saved local version; save a separate local copy first if needed. **Keep local as a separate provider draft** preserves the external copy and publishes the local version separately.
- If a provider draft disappears, Spindle cannot distinguish sending, deletion or movement by another client. It records a conflict and does not recreate or send it automatically. Review the native client before explicitly keeping the local version.
- Discarding, changing the selected account or full SMTP acceptance schedules deletion of the tracked old copy. Changed provider copies remain conflicts. Cleanup issues remain in **Local drafts** after the local draft disappears; **Leave original provider copy** acknowledges keeping it. Disconnecting an account preserves local content and leaves provider copies in place because its credentials/mapping are removed.

Complex native HTML stays in a sanitized **Original draft content** snapshot below the editable note. Styles, tables and supported inline raster images are retained through the existing isolated preview and outgoing MIME path. Images start blocked and can be displayed explicitly. Add edits above this preserved body, or edit its structure in the native client. Plain-text selection converts the whole outgoing body to text. Simple HTML imports into the editor directly. Script/unsafe content is removed. Recipient syntax may be normalized by MIME clients; complete validation still occurs at Send.

## Recovery and safety

The account lease fences every database commit and provider mutation, sharing the existing two-connection worker budget. API/list/status paths read Postgres only. Each upload records a durable operation UUID, Message-ID, target folder and expected MIME hash **before APPEND**. A restart searches for that operation before doing anything else. An unconfirmed APPEND becomes **unknown**, including a crash before the write; **Check provider again** searches and never blindly appends a second copy. If it cannot be found, keep using the local draft or explicitly save a separate draft after reviewing the provider. Unknown/conflicted drafts cannot send through Spindle.

Replacement appends the new copy before removing the old tracked copy. UIDVALIDITY/UID, operation markers, exact Message-ID and MIME hashes detect replacements and external edits. Ambiguous matches preserve copies and require review. If another client replaces the UID, removes the operation marker and changes the Message-ID, identity cannot be proven: the old mapping becomes a removal conflict and the new draft can be imported separately. Cleanup rechecks content and requires UIDPLUS for targeted expunge; it never broad-expunges unrelated messages, even on an IMAP4rev2-only server. Servers without UIDPLUS can accept an initial copy but replacement/cleanup require review. Temporary duplicate copies can be visible between APPEND and cleanup or after interruption.

Before SMTP delivery, the worker rechecks an existing provider copy. Detected outside changes fail the queued send and preserve both versions. An unavailable provider check fails safely and permits retry later. IMAP and SMTP cannot provide a transaction across other clients: an edit immediately after this check or an independent send by another client cannot be prevented. Unknown/partial SMTP delivery retains the local draft and provider copy; neither is blindly retried. Existing Outbox rules remain authoritative.

All routes, files, mappings and jobs enforce verified private ownership; admins have no mail-content exemption. Error codes are allowlisted. Native ordinary files enter the existing pending-scan pipeline and must pass ClamAV before they can be uploaded again or sent. Unchanged owned files are reused only after matching filename, size and SHA-256 chunk fingerprints. Conflict files remain referenced until resolution.

Limits reuse 100 local drafts, 10 ordinary files/draft, 10 MiB/file, 20 MiB aggregate and 256 MiB/user outgoing storage. Raw Draft MIME is bounded to 30 MiB, parsed body input to 2 MiB and editable canonical content to 120,000 bytes. Formatted snapshots use the existing forward-content limits. Unsupported embedded images, oversized drafts and quota failures stay available in the native client, with a visible import failure and retry. Each worker job processes at most four links and two imports. ImapFlow requires a Buffer for APPEND, so each bounded draft operation buffers at most 30 MiB; SMTP stays streamed.

## Upgrade and rollback

Apply additive `0016_provider_drafts.sql` before deploying the new API/web/worker. It adds owner-scoped mapping, copy-intent, conflict-file and import-intent tables plus local draft triggers, and backfills existing drafts with selected accounts. It does not rewrite draft text, SMTP credentials or frozen Outbox MIME. The worker will begin mirroring existing selected-account drafts after deployment. No new environment settings or dependencies are required.

For rollback, stop the new worker first and retain the migration, copy history and local drafts. Earlier application code can keep saving local drafts; the database triggers retain intent for the next upgrade. Do not remove mappings/tables or reset Outbox states as a rollback shortcut. Earlier workers do not reconcile remote edits or perform the new pre-send check, so suspend outgoing processing if relying on those protections. Copy/import tombstones currently remain until account removal; retention pruning is later operational work.

Synthetic integration and Chromium checks cover provider visibility/replacement, imports, scan gating, Bcc/threading/MIME, ownership/origin denial, clean and dirty editors, conflicts and resolution, discard/accepted-send cleanup, unknown SMTP preservation, lease loss, UIDVALIDITY changes, UIDPLUS refusal, unrelated deleted messages, saves/discards during APPEND, lost acknowledgements and durable dispatch. Real-account cross-client visibility/editing, provider-specific MIME normalization and restart acceptance remain part of I11.
