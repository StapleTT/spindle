# Administration in Settings

Verified, active administrators see Settings → Admin. Regular users do not see the tab, and saved browser state cannot enable it. Administrators initially see only a password gate; the management UI and all admin data remain hidden until the gate is unlocked. Every `/api/admin/*` request independently checks the authoritative Better Auth session, verification, suspension and current role. Administration never grants access to another user's mail, attachments, drafts, provider credentials or sessions' bearer tokens.

## Shipped controls

- **Users:** search by profile name or email; view role, verification/suspension, join date, connected-account count and active-session count. Results are bounded to 25 per page.
- **Access:** suspend/resume, sign out all devices, and promote/demote administrators. Confirm the acting administrator's current Spindle password once to unlock the section for the current sign-in session. Subsequent actions keep their confirmation dialogs without asking for the password again. Role changes revoke the target's sessions. Self access changes are refused; use another administrator for role/suspension changes and the existing Security/account menu controls for personal sessions.
- **Invitations:** send, resend and revoke seven-day email-bound invitations using the existing configured authentication mailer and branded invitation template. The panel issues regular-user invitations; promote a verified account afterward. Initial-admin invitations remain operator managed. Show pending, accepted, revoked and expired invitations, with separate sent/failed/unknown delivery status. A delivery failure leaves the saved invitation visible and offers an explicit resend. Revocation affects registration eligibility, not an already-created user.
- **Activity:** paginated records of committed access, role, session and invitation changes, including actor, target, time and non-secret resulting state. The overview shows user, suspension and pending-invitation counts. Full operational monitoring and authentication-event auditing remain separate work.

Unlock is stored only on the current server-backed Better Auth session, never in a client flag. It survives tab changes, reloads and API restarts for that session; another device or a fresh sign-in starts locked. Unlock rechecks the confirmed credential hash, active session, role, verification and suspension under the existing locks. Every subsequent read requires the unlock, and mutations recheck it transactionally together with the current session and privileges. Password/email changes, sign-out, session expiry/revocation and suspension remove it with the session; role/verification changes also clear it. Passwords are never stored in browser storage, audit records or request logs. Owner-scoped persistent budgets allow 120 admin reads/minute, 10 writes/minute and five unlock password confirmations/minute, in addition to existing authentication limits. All writes require the exact configured Origin; input shapes, search/cursors and request bodies are bounded. Search treats `%` and `_` literally rather than as arbitrary SQL patterns.

## Suspension and provider work

Suspension is independent of email verification. A database trigger revokes sessions and user-bound recovery/email-change links, invalidates account leases and fences in-progress upload/scanner tokens. The API, content host, SSE validation, dispatcher, IDLE watches, worker claims and guarded commits check `NOT suspended`. Existing streams terminate on their next session check; IDLE's existing heartbeat closes a fenced watch. A new session cannot be inserted for a suspended owner, including a concurrent login racing suspension.

Mail, cached content, settings, drafts and queued/scheduled intents remain saved. No new provider operation is claimed while suspended. A provider operation already submitted cannot be undone by suspension and may complete externally; lease fencing refuses its late local commit. Preserve existing unknown-send/APPEND recovery rules rather than automatically resending. Resume permits fresh login and background work; revoked sessions stay revoked. Queued mail and overdue scheduled sends may dispatch after resumption, as the confirmation explains. Existing bounded storage cleanup/expiry still applies.

## Consistency and audit

Admin mutations share the operator invitation advisory lock, then lock acting owner, credential/session and target in that order. Recheck role, suspension, verification, unlock and session expiry inside every mutation transaction; also recheck the credential hash when unlocking. Expected user revisions and invitation IDs reject stale writes. Database last-active-admin protection also refuses demotion, suspension or deletion of the final enabled administrator. The unlock covers administration only; personal Security password/email/session controls retain their own password confirmation. The panel refuses self access changes, including session revocation; two admins cannot concurrently demote each other and leave no active administrator.

Every mutation uses a client-generated UUID operation ID, recorded with a hash of the non-secret intent in `admin_audit`. Replaying the same operation returns its recorded outcome without repeating the change or sending another email; reusing it for another intent fails. A network failure preserves this operation ID in the confirmation form for a safe retry. Audit and mutation commit together. No passwords, verification/session tokens, mail content, provider settings or recipient lists enter these records.

Invitation eligibility is locked and checked inside the existing transactional Better Auth registration path; successful signup marks the invitation accepted with a stable user ID. Resend creates a new invitation ID; delayed delivery cannot overwrite a newer invitation's status. Delivery follows the committed invitation, so a crash can leave delivery unknown. An explicit resend is the recovery path. A revoked invite cannot create a user in invite mode; public registration remains governed by the existing release policy. Expired/accepted invitations do not re-grant an administrator role.

## Installation and rollback

Append migrations `0032_admin_settings.sql` and `0033_admin_unlock.sql`; do not modify earlier migrations. It adds suspension/revision fields, invitation lifecycle metadata, `admin_audit`, last-admin and session/suspension guards. Migration 0033 adds a nullable `admin_unlocked_at` to sessions and clears it on role/verification changes. Existing sessions start locked, with all session IDs/tokens/expiry unchanged. Existing users default active with unchanged roles. Existing invitation/user matches receive accepted metadata; existing authentication, mail, credentials, drafts and queued bytes remain intact.

Stop old API/worker processes, run `npm run db:migrate`, deploy the new API/worker/web together and restart. Do not run an old worker alongside suspension-aware administration: old workers do not understand the new suspended flag. The current initial administrator sees the tab after signing in/refetching the session. For a new installation, continue using `npm run auth:invite -- email@example.com --admin`; signup order never grants administration. No existing account is automatically promoted by this feature.

Leave additive columns, records and triggers in place during application repair/rollback. An older Admin release does not enforce the read gate: keep admin endpoints unavailable during such a rollback rather than exposing management data before password confirmation. If suspended users exist, keep old workers stopped; prefer forward repair, or first perform an explicit reviewed restoration of access using suspension-aware code. Do not silently resume suspended users, clear audit history, restore revoked sessions or reset the database to make an older binary run. Restoring a backup also cannot undo external mail already sent; existing isolated-restore/no-resend requirements remain.

Tests use synthetic users/provider settings and a mocked email transport; no real recipient receives test invitations.

See `REBUILD_TASKS.md` for final command results and local migration preservation evidence. User deletion/export, retention policy, broader authentication auditing, bulk operations, operational metrics/alerts and help/legal pages are not implemented by this slice. Live invitation delivery for the panel, manual screen-reader review, additional browser engines and user visual acceptance remain open.
